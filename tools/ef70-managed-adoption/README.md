# EF70 canonical managed adoption

This finite hosted job runs the published managed controller for the actual
Extension Foundation PR #70 source commit. The consumer source is the real EF
push `github.sha`, captured from a clean checkout with its exact tree and file
inventory. The earlier seven-chain campaign remains bound to its own historical
source and results.

## Selected inputs

The reusable workflow `.github/workflows/ef70-canonical-adoption.yml` accepts
four explicit inputs:

| Input                | Required binding                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `harness_revision`   | Exact reviewed Engineering Foundation source commit checked out by the job                                       |
| `preflight_run_id`   | Actual successful attempt 1 of that commit's ordinary producer preflight                                         |
| `authority_revision` | Exact current protected Central main containing the qualified target                                             |
| `target_cohort`      | Actual qualified EF canary record with the admitted generation3 package, runtime, policy and closure coordinates |

The producer preflight runs on `test/ef70-canonical-adoption`. It preserves the
ordinary installation, source build, explicit Stack cleanup, unchanged-source
check, frozen managed test tools, complete changed-file checks, fast route and
workflow security checks. Focused native tests cover the new launcher's admission
and failure observations. This is source feedback, not trusted consumer admission
or a substitute for required repository CI.

The actual transition runs only in the real EF repository and existing PR #70
branch context. Three sibling checkouts hold EF, the immutable harness and
Central. Fresh owned caches, controller installation and evidence directories
live outside the consumer. The implementation validates the selected record's
reusable-workflow revision and the exact reviewed receipt-authorization repair;
a different revision string alone does not establish the repair.

## Operation and evidence

The job authenticates the frozen published controller installation before its
first public CLI call, including actual archive identities, installed bytes,
signature coverage and release provenance. It uses physical Node24.22.3 and
Node26.12.1 with the selected Corepack and package-manager versions. Source
installation disables scripts and pnpm hooks, preserving the old compiler floor
guard. The unchanged standalone lock composer selects fresh inputs from the
actual consumer and Central checkouts.

The finite sequence is `upgrade --prepare`, `finalize`, then the installed target
adapter's `check`. Preparation paths and digests come from the actual prepare
response. Every process has retained arguments, timing, exit or signal, stdout
and stderr. Source images must remain unchanged after prepare. Successful
finalize must produce the real receipt and completion, exact managed afterimages,
unchanged foreign images and a successful installed-target check.

The evidence package contains actual source and harness identities, authority and
cohort bindings, authentication observations, selected lock, raw owner proofs,
command captures and the real managed file delta. `adoption-complete.json` marks
only this completed sequence. It does not mark the seven-chain campaign complete
or create a trusted Docs qualification, observed binding or CANARY event.
Failure retains its actual observations and stops the sequence. Public CLI and
package subprocesses receive no observer credentials. Anonymous API pacing may
wait for the observed reset before launch; a managed operation is never retried
automatically.

## Applying the result

The receiver verifies the original consumer commit and actual generated files
before updating the existing PR #70. Host changes and the posttransition
assertions/documentation follow successful managed completion; their overlap
with the actual managed path set must be checked again. Historical preparation
bytes keep the original runner root identity and must not be rewritten to match
a receiving checkout.

Committed-target recovery uses the published explicit current-selection route
and its actual source ancestry. Qualification on the PR branch does not establish
that the original preparation selects a later squash-merge lineage. Final native
and trusted CI, protected merge, default-main checks, archive/LMU reconciliation,
observed binding and CANARY remain separate genuine results.

This producer validation branch is not intended to merge. It adds no production
controller implementation or consumer-domain authority to Engineering Foundation.

# ADR-0027: Stage Docs Protocol Publication After Foundation

Status: Accepted

Date: 2026-08-14

Decision owner: Product owner

## Context

Docs Protocol depends on the new Foundation document-materialization API. A
single Changesets wave cannot prove the first Docs Protocol registry artifact
against an already available exact Foundation 0.17 RC without making release
ordering, bootstrap credentials, and first-version evidence implicit.

ADR-0026 remains the active authority for directory materialization and carries
the unified protocol architecture from ADR-0025. This decision complements it
and overrides only the rollout publication sequence described by ADR-0025 and
the release procedure; it does not replace any technical or ownership decision.

## Decision

1. Stage one releases only `@agent-teams/engineering-foundation` as
   `0.17.0-rc.0`. Docs Protocol remains fully built and qualified at `0.0.0`, but
   its production manifest is `private: true`, has no publish configuration, is
   ignored by Changesets, and is absent from the publishable-package catalog.
2. Stage-one release preparation, cleanup, generated-release validation, and
   publication own only the current public Foundation package. The existing
   private parser spike policy remains unchanged.
3. Hermetic registry qualification may copy Docs Protocol into an explicitly
   disposable fixture, remove `private` only in that copy, bind its Foundation
   dependency to the exact packed Foundation version, and publish the fixture
   only to the no-uplink test registry. This does not make the production package
   publishable or release-owned.
4. After Foundation `0.17.0-rc.0` is published and verified, a separate reviewed
   bootstrap PR may make Docs Protocol public. It must remove the Changesets
   ignore, restore public provenance configuration, prove its packed dependency
   resolves to the available exact Foundation `0.17.0-rc.0`, add the real
   `0.0.0` changelog entry, and prove public-API bootstrap promotion is an exact
   no-op against the already reviewed baseline.
5. The bootstrap PR must not add a permanent token workflow. Hosted publication
   performs the one-time `0.0.0` package publish, exact tag and GitHub release,
   and any required deprecation using a bounded temporary npm credential with
   provenance. npm trusted publishing is then configured and verified, and the
   temporary credential is revoked.
6. Only after the bootstrap artifact and trust boundary are verified may a Docs
   Protocol minor Changeset generate `0.1.0-rc.0`. That release uses the normal
   protected-main Changesets and trusted-publishing path.
7. Versions and prerelease state are always generated by Changesets except for
   the intentional first `0.0.0` bootstrap artifact. No consumer adoption starts
   until both exact RC packages are available and registry-qualified.

## Consequences

- Foundation's new mechanism is independently available before its dependent
  package can enter the public registry.
- The source implementation and public API baseline receive normal review in
  stage one without granting production publication authority to Docs Protocol.
- The one-time npm bootstrap remains explicit, auditable, and removable rather
  than becoming a permanent privileged workflow.
- The rollout requires two release gates, but each gate has one unambiguous
  package owner and a verifiable registry dependency graph.
